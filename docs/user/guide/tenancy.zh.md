# 一套部署服务多人

[English](tenancy.md) | 中文

会服务浏览器的 profile——`qilin` 与 `qilin web`——在一个地址上服务整套部署：访客在该地址登录，每个账户在 `$QILIN_HOME/tenants/<账户 id>/` 下得到自己的引擎运行时——自己的会话、任务、工作区、附件、插件、模型设置、凭据、技能与预设。只有账户名册是共享的。每个运行时都保留账号门，并且只接纳它服务的那个账户。

## 创建账户

名册是 `$QILIN_HOME/auth/accounts.json`，由入口与所有运行时共享。租户运行时关闭注册且只接纳它服务的那个账户；首启运行时承载的则是部署自己的策略，因此接受新账户的部署也通过产品的注册表单扩充账户。下面这些命令用于无需浏览器地创建账户、重新设置密码与注销账户。

```sh
qilin tenants accounts                                  # who is in this home
qilin tenants add alice                                 # prompts twice, without echoing
printf '%s\n' "$PASSWORD" | qilin tenants add bob --password-stdin
qilin tenants passwd alice                              # re-key; issued sessions stop verifying
qilin tenants remove alice [--purge-data]               # retire; keep Sessions unless purged
```

`--admin` 创建这套部署**唯一**的管理员席位：唯一性在名册锁内检查，因此第二个会被拒绝，而不是被静默加入。只有该席位的运行时可以读取整套部署的 token 账本；其他账户各自只读自己的。

## 启动整套部署

```sh
qilin --port 8790
```

入口会打印自己的 URL（默认 loopback 与 8790 端口），在请求指名某个账户时启动它的运行时，并回收没人使用的运行时。入口自己不作画：落地页、登录表单与注册都归每个运行时内部的应用所有。`--idle-ms` 设定这个空闲窗口，`0` 表示让每个运行时都保持存活。`--max-tenants` 通过回收最久未使用的那个来限定同时存活的运行时数量。`--restart-backoff-ms` 设定启动失败的运行时第一次重试前的等待；每次连续失败该等待翻倍，而 `/status` 会报告失败次数与最早的重试时间。`--registration open|closed` 决定产品自己的表单能否创建账户：loopback 地址上默认为 open，其他地址上默认为 closed，因此别的机器能到达的地址只在运维明说时才创建账户（用 `qilin tenants add`）。每个账户的运行时还会把它那些会话的消耗报给部署自己的账本：hub 为每个运行时铸一个令牌，并只在一个仅回环可达的地址上收报告，因此一份报告记在**铸出该令牌的账户**名下，而不是记在请求体自称的账户名下。账本是每账户一个 JSON Lines 文件，放在 `$QILIN_HOME/tenants/.usage/<账户 id>.jsonl`，以 `0600` 写入 `0700` 目录。入口用它应答账户自己的用量读取，并靠该运行时的凭据限定作用域，因此已登录的账户只可能读到自己的。

两个 flag 决定浏览器如何到达每个运行时。`--tls-cert` 与 `--tls-key` 指一对未加密的 PEM，必须成对给出，并让入口终止 TLS——这是每个运行时把自己的会话 cookie 标为 `Secure` 的唯一条件。`--tenant-host` 则是把每个账户运行时直接暴露在指名的接口上，这正是入口前面的反向代理需要的形态；因为终止 TLS 的不是入口本身，cookie 不会被标记。`--per-account-ports` 给每个账户自己的 origin 与 cookie 罐，这也是同一个浏览器同时登录两个账户的办法；不用它时路由 cookie 是浏览器级的，一个浏览器一次只驱动一个账户。

`--max-tenants` 大于零时，两个账户同时到达可能争抢最后的名额：一次交接会回收一个运行时，而输掉的那次请求可能看到 `503`。这是上限在起它的作用——想留住每个运行时，就保持默认的 `--max-tenants 0`。

## 在这个地址登录

无论名册里有什么，`/` 都由**产品自己的落地页**应答：这套部署不作账户列表，也不显示任何账户名。登录与首启文档，以及它们背后的账户面（`/api/auth/*`），是**部署自己的门**：由承载部署注册策略的首启运行时应答——哪怕这个浏览器此前已经选过账户；因为租户运行时把准入收窄到一个账户，而账户插件要求这种收窄必须保持关闭注册，所以它既不能提供注册，也不能把浏览器登成别人。每次门的应答都会丢掉路由 cookie，因为来到门前的浏览器正在重新选账户。`/t/<账户>/` 直接指名一个账户，是你要指定某个账户时该发出去的地址。部署从不列出自己有哪些账户。登录之后，路由 cookie 把每个请求——应用文档、`/api`、mux 升级与带 Range 的媒体读取——分派给那个账户自己的运行时，同时把运行时自己的 authority 顶替掉入口的，从而让它的会话 cookie 始终绑定在签发它的那个运行时上。

名册里尚不存在的名字，以及指向一个名册已不再持有的账户的路由 cookie，都到达同一个首启运行时：浏览器到来时没有账户，接下来由应用决定——部署接受新账户时给出它的注册表单，不接受时给出它自己的拒绝。

同一个浏览器一次只服务一个账户；`/healthz` 与 `/status` 仍归入口自己读取，而回收统计的是被代理的流量。运行时默认只绑 loopback，因此浏览器需要的地址只有入口那一个；`--tenant-host` 指定别的接口时，每个账户运行时会直接暴露在该接口上——明文 HTTP、各自独立的 cookie 罐、中间没有入口——那个接口因此需要与入口地址同等的保护。

## 各种东西放在哪里

| `$QILIN_HOME` 下的路径 | 存放什么 |
|---|---|
| `auth/accounts.json` | 名册：身份、邮箱、scrypt 哈希，以及管理员标记 |
| `auth/session-secret.json` | 这套部署全部会话所用的签名密钥，`0600` 于 `0700` 目录内 |
| `tenants/<账户 id>/` | 该账户的引擎 home：会话、任务、工作区、附件、插件、模型设置、凭据、技能、预设 |
| `tenants/.usage/<账户 id>.jsonl` | 该账户的 token 账本，每个已结算的 Turn 一条报告 |
| `tenants/.bootstrap/` | 首启运行时的 home，仅在名册为空时使用 |

`/status` 报告入口知道的每个运行时：账户、状态、origin、启动次数、连续失败次数与最早重试时间。`/healthz` 应答存活。某个运行时自己的日志行会以 `qilin tenants: [<账户 id>]` 为前缀出现在入口的标准错误上。

账户的用量页读取 `GET /api/usage/me`：入口用该运行时的凭据从部署账本应答它，因此一个页面只可能读到自己的账户；管理员席位在那里的读数则是每个账户的数字。运维直接读账本文件这条路仍然存在，且不需要任何页面。

**替换或清空 `auth/session-secret.json` 会让所有已签发的会话一次性失效**：浏览器重新登录，而账户数据一点都不动。`qilin tenants passwd` 对单个账户做同样的事。重启入口就把新构建应用到每个账户；除此之外没有别的东西需要重启。

## 查看名册与注销账户

`qilin tenants remove` 把账户从名册中移除，并把它的会话留在磁盘上；加上 `--purge-data` 会连同该账户的租户目录一起删除，那些会话也就随之消失。已经在提供服务的运行时会继续应答，直到它被回收或整套部署重启。此后启动的运行时会在加载时失败，因为它的覆盖层接纳的是一个文件里已不存在的账户——这是刻意的，也正是它让「注销」这件事可见而不是静默。

## 哪些共享，哪些不共享

| 状态 | 归属 |
|---|---|
| 会话、任务、工作区、附件、插件、模型设置、凭据、技能、预设 | 创建它们的那个账户 |
| 账户名册（`$QILIN_HOME/auth/accounts.json`） | 这套部署 |
| 会话签名密钥（`$QILIN_HOME/auth/session-secret.json`） | 这套部署——一个会话在每个运行时都有效 |
| token 账本（`$QILIN_HOME/tenants/.usage/`） | 这套部署，每账户一个文件 |

## 部署前须知

- **文件系统不是边界。** 每个运行时都以同一个操作系统用户运行，因此 agent 的 shell 与文件工具可以读取其他账户的目录和共享的凭据文件。同一套部署上的账户是协作方。
- **每个账户配置自己的 provider。** 模型凭据存在账户自己的 home 里，因此一把 key 只属于一个账户；每个账户花了多少由部署账本归集，运维读全量，账户自己只读自己那一份。
- **安装插件按账户进行。** 每个运行时都装进自己的 home；不存在需要加锁的部署级插件集。
- **每个账户是一个进程。** 内存与端口随同时存活的运行时数量增长，空闲窗口与并发上限正是为此存在。
- **一次升级同时影响所有账户。** 这通常正是你要的，但它使升级成为一次部署级操作。
