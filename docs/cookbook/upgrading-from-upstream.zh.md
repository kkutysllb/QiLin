# 从上游 DSH 发行版升级

[English](upgrading-from-upstream.md) | 中文

如何把上游 DSH 的新版本拉进本 fork。除 vendored Cordis（`vendor/`）外，本仓的每一个包都是重写——因此升级绝不是合并，而是以落盘的计划驱动的逐包对齐，并以全仓审计收尾。计划先行：计划未落盘，任何代码都不动。

## 铁律

1. **计划先行，代码不动。** 先在 `plans/` 落两份文档——差异分析和对齐实施计划——然后才允许触碰任何源码、清单或锁文件。两份计划落盘且待澄清问题清零之前，唯一允许的写入就是计划本身。
2. **官方发布说明逐行对账到代码级变更点。** 逐条走读上游发布说明，标记每条在本仓的落点；再挖掘说明未提及的变更——实际 diff 才是权威，不是说明文本。
3. **自研内置插件逐项做升级点分析。** 技能族（`packages/skill/*` + `ui-skill` + `ui-settings-skills`）与 MCP 族（`packages/mcp/*` + `ui-settings-mcp`）是本仓自有代码：对每一族，明确说出哪些上游变更会触及它、它的升级点是什么。
4. **第三方与非内置自研插件做启动炸梳理。** 上游破坏性变更可能炸掉本仓不随发的插件：逐条破坏性变更对照 `dsh-compat` 兼容面与 cordis 插件契约，记录哪些外部插件能启动、哪些会炸、哪些有兼容垫片兜住。
5. **逐包对齐，因为一切皆重写。** 除 vendored Cordis（钉死的源码副本原样使用）外，本仓每个包都是上游对应包的重写：逐包对齐——上游变更 × 本仓重写差异 × 采纳/改后采纳/不采决策——并趁上游工作新鲜时登记完善自研包功能的机会。
6. **以六维全仓审计收尾。** 死代码、冗余代码、安全漏洞、功能断点、接线遗漏、业务逻辑断点——每一维都要有工具运行或有依据的清查，并在对齐计划里记录结论。
7. **存疑即抛澄清卡。** 凡产品语义不确定的点，以卡片形式抛给用户——问题、背景、选项、建议默认值——并在依赖它的批次开工前得到拍板。猜测产品语义即触红线。

## 阶段 P0——差异分析

产出 `plans/<日期>-upstream-<版本>-delta-analysis.md`。基于上游实际 diff 工作，不是只读说明。必需章节（形制范例见 `plans/2026-09-30-upstream-0.2.0-rc.2-delta-analysis.md`）：

1. **硬事实速览**——引擎/内核稳定性结论一览。
2. **官方发布说明逐条 → 代码级变更点**，按新增、修复、优化、其他分组。
3. **发布说明未提及的代码级变更**，拆为内核/引擎（模型可见或破坏性）、客户端、升级断点、构建/CI。本节是点名未文档化行为变化的地方——未提及变更从 diff 里挖，所以必须引用文件，不能只引说明。
4. **引擎功能与内核差异总结（对照本仓当前树）。**
5. **自研内置插件逐项**：技能族、MCP 族，然后是本次发行触及的每个其他自研族（侧边栏衍生、终端等）。每一族：上游变更、本仓重写差异、升级点。
6. **第三方与非内置插件启动梳理**：每条破坏性变更 × `dsh-compat` 面与 cordis 契约暴露的插件入口路径，对每类受影响插件给出能启动/会炸/有垫片结论。
7. **逐包对齐清单**（cordis 除外）：每包一行——上游变更、本仓重写差异、决策、以及完善自研功能集的机会。
8. **优先级建议、品牌红线、遗留核对项**——包括将要变成澄清卡的问题。

## 阶段 P1——对齐实施计划

产出 `plans/<日期>-upstream-<版本>-alignment.md`。必需章节（见 `plans/2026-09-30-upstream-0.2.0-rc.2-alignment.md`）：

1. **已确认决策**——每张澄清卡及其结论与日期。
2. **红线**——每批开工前自查；命中即停。品牌红线、vendored Cordis 冻结、已发行 Session 格式冻结，以及差异分析标记的一切。
3. **批次切分**——典型为 B0 预检、引擎/内核批先行（最小的降险批早走），随后服务/配置/持久化接缝，再到客户端接缝（冲突集中的三方合并区），然后文档/生成器/门禁，最后总验证批。
4. **风险登记、遗留登记、完成判据。**
5. **批次执行状态**，随执行追加，收口时写收口条目。

## 阶段 P2——升级后六维审计

最后一个代码批之后、宣布发行之前执行。每一维产出结论与处置，追加到对齐计划：

| 维度 | 做法 |
|---|---|
| 死代码 | 清查本次升级中失去最后一个消费者的导出与文件（对 `packages/`、`apps/`、`scripts/` 做引用图）；删除或记录保留理由。 |
| 冗余代码 | `pnpm run duplication` 对照升级前基线；新增重复必须搬迁或说明理由。 |
| 安全漏洞 | `pnpm audit --prod` 加上对升级新增/升级项的 lockfile 审查；每条发现给出修复/接受/延期及理由。 |
| 功能断点 | 逐项回验差异分析的决策清单：每个采纳的上游功能在本仓可用，每个不采的都记录理由。 |
| 接线遗漏 | verify 族全开：`verify-client-catalog`、`verify-kylin-catalog`、`verify-config-catalog`、`verify-module-graph`、`verify-doc-graphs`、`verify-package-dependencies`、`hygiene`、`doc-sync`。目录过期就是断线。 |
| 业务逻辑断点 | `pnpm run test`、`pnpm run test:snapshot`、`pnpm run test:expected`，有 key 时加 `pnpm run test:e2e`；失败在证明清白之前都按业务逻辑断裂处理。 |

## 验证阶梯

宣布升级完成前按序执行：`pnpm run typecheck` → `pnpm run test:gui` → `pnpm run lint` → 阶段 P2 审计族 → `pnpm run build` → `pnpm run test:docs`。红门即停止宣布发行；升级开始前就红的门记为既有问题移交清扫窗，不得静默无视。
