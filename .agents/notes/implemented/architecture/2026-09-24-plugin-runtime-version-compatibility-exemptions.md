# Agent Note: Plugin runtime-version compatibility with per-profile exemptions

Status: implemented

English | [中文](2026-09-24-plugin-runtime-version-compatibility-exemptions.zh.md)

## Problem

A plugin declares the harness packages it needs in `peerDependencies`, but nothing read those ranges before plugin code ran. A plugin built for a different harness release installed normally, mounted normally, and failed later as an unexplained registration or API error — the same failure class the [DSH plugin compatibility note](2026-09-15-dsh-plugin-ecosystem-compat.md) attributes to a second engine copy, reached from the other direction. Refusing an install that names an incompatible package needed a decision the operator could overrule for one package, because a working deployment can legitimately depend on a plugin whose declaration lags the release.

## Decision

**Declared `@qilin/` peers are checked against the running runtime version at every admission point, and a profile may exempt one exact plugin/runtime pair.** The runtime version is `getQilinRuntimeVersion()`, read from the app-boot manifest, so the value `qilin --version` prints is the value compared. A peer participates when it is scoped `@qilin/` and is not a vendored framework, foundation, or Loader plugin package: `@qilin/kylin`, `@qilin/cosmokit`, `@qilin/schemastery`, `@qilin/node-addon-system`, and `@qilin/kylin-plugin-*` version independently of a harness release, so comparing them against it would refuse every plugin that declares them correctly. `workspace:^`, `workspace:~`, and `workspace:*` mean the running runtime; prereleases take part in ranges. A malformed or absent range is a mismatch, and a mismatch on a manifest with no own non-empty `name` or `version` throws rather than reporting anonymously.

**The exemption is profile-local metadata with its own file, and an unreadable one fails closed for writing.** `compatibility.json` sits in the profile directory beside `package.json` and `cordis.patch.yml`; it is written atomically with mode `0600` under its own file lock and holds exact `package-name@version` keys mapped to lists of exact runtime versions. Writing it changes no dependency, no bundle selection, and no patch layer. Reading is deliberately fail-open for the profile: a missing file authorizes nothing, and a file that cannot be read or parsed authorizes nothing while reporting every rejected record and keeping the records it accepted, so a bad file can never make a profile unbootable. Writing is the opposite. Any rejected record makes the file `rewritable: false`, and a grant or revocation then refuses with the reader's warnings instead of rewriting the document, because a rewrite would discard content the operator must repair by hand. Repair is the operator's, and it is the only way to make the file writable again.

**Authorization covers only the exact rejected pair, and a grant may name only the running runtime.** The key is the plugin's own name and version as installed, never an installation spec, alias, or range, and the value is compared against the running version exactly, including build metadata. A plugin upgrade, a downgrade, or a runtime upgrade therefore inherits nothing. A grant additionally requires `acceptRisk: true`, which the caller sets only after the operator has been told that an incompatible plugin may crash the application or corrupt data; the service checks that acknowledgement and the identities, never conversation history. A grant naming any version other than the running one is refused and names the current version instead. Revocation takes no acknowledgement and may name a historical runtime, so withdrawing an approval left by an earlier release stays possible, and revoking one of a pair's runtimes leaves its other grants intact.

**Four admission paths apply the same policy, and two of them are not plugin rows.** Plugin rows reach the Loader through `prepareProfileEntries`/`prepareProfilePatches`, so a denied row mounts disabled before any plugin code is imported and an Include that reaches a denied plugin is denied as a whole. A bundle row is not a plugin row, so row admission never reads its own peers: `loadProfileDirectory` evaluates every `qilin.profile.bundles` entry and fails startup loudly for one the profile does not exempt, beside a bundle that declares no patch. A preset row reaches its tree through `mountPreset`, whose entry group routes every `Include` update through the same admission, so an agent preset declares a denied plugin as intentionally inactive instead of a failed import. An install command is judged before pnpm runs where the named manifests can be read — a path from disk, a registry spec through pnpm's own lookup — and after installation where they cannot, a git or tarball spec or a bundle component whose peers need the installed tree; a refusal restores `package.json` and the lockfile, and a dependency the run did not touch never blocks an unrelated operation.

**Refusals are typed and name the remedy.** `ManagementError.code` gains `incompatible-version`, carrying `IncompatiblePlugin` records (`name`, `version`, `runtimeVersion`, and only the unsatisfied `peers`), which each surface renders itself: the Web page through its locale dictionary, the tool result as JSON, and the CLI as the exact `allow-version` command for each refused package. The CLI exposes `qilin plugin --profile <profile> version-exemptions`, `allow-version <package@version> --qilin-version <exact> --accept-risk`, and `revoke-version <package@version> --qilin-version <exact>`; the same operations reach the model as `plugin_manager` actions `list_version_exemptions` and `set_version_exemption`. A grant takes effect on the next composition: a live profile recomposes and reports `applied`, a startup-only profile reports `restart-required`.

The `version-exemptions`, `allow-version`, and `revoke-version` verbs are QiLin-local additions to the upstream port: upstream's CLI delegates every forwarded argument list to the shared profile operations, while QiLin's `qilin plugin` keeps its own pnpm invocation for the DSH-era engine-name refusal and two-channel bundle reconciliation, so it calls the shared pre-install check directly instead.

## Alternatives considered

- Storing exemptions in the profile's `package.json` was rejected because the profile manifest is the user's own package project: a grant would appear as a dependency edit, be rewritten by ordinary pnpm commands, and be indistinguishable from a bundle selection.
- A single `compatibility.json` without a write refusal was rejected because the reader deliberately keeps the records it accepted: silently rewriting a file that also contains a rejected record would delete the operator's text with no report.
- Pre-granting a range, a plugin name without its version, or a future runtime was rejected because the risk is specific to one loaded pair, and a grant that outlives the version it was made for is an unreviewed approval.
- Treating the vendored framework packages as runtime peers was rejected because `@qilin/kylin`, `@qilin/cosmokit`, `@qilin/schemastery`, and `@qilin/node-addon-system` carry their own versions, so the rule would refuse correct plugins.
- Skipping a refused bundle instead of failing startup was rejected because a profile that lists a layer it does not run is misconfiguration, and the profile loader already fails loudly for a listed bundle without a patch definition.
- Warning without refusing was rejected because the install would already have run build scripts and replaced `node_modules`; the check exists to keep an incompatible version off disk.

## Consequences

A plugin whose declaration lags a compatible release needs an explicit grant per package, per runtime version, which is deliberate friction: the grant is the record that a human accepted the risk. A grant is not portable between profiles, and an operator who copies a profile directory must copy `compatibility.json` with it. A refused pre-install leaves nothing on disk, but a post-install refusal restores the manifest and lockfile and reinstalls the restored lockfile, so already permitted build-script effects may remain. A dependency the run did not touch stays installed and only warns; profile startup is what denies it. A `compatibility.json` that contains a rejected record blocks every grant and revocation until repaired by hand, which is fail-closed by design and is the one state an operator must resolve outside the product. The peer rule only covers `@qilin/` names, so a plugin that declares no harness peer at all is admitted and judged at runtime as before.

## Verification

`packages/boot/app-boot/tests/plugin-compatibility.spec.ts` pins the runtime-version read, range semantics including prereleases and `workspace:` forms, the vendored-package exclusion, malformed manifests, and exemption identity including prototype-named plugin names. `profile-compatibility.spec.ts` pins exact identities, owner-only mode, malformed-record handling, the write refusal, and historical-runtime revocation. `compatibility-preflight.spec.ts` boots real profiles and asserts that a denied plugin is never imported, that only the exempted pair is admitted, and that bundle-row and preset-row admission behave the same. `profile.spec.ts` pins the loud bundle refusal and its exemption. `apps/cli/tests/plugin.spec.ts` pins the three verbs, their malformed inputs, and the pre-install refusal, and `plugin-compatibility.expected.e2e.ts` installs, boots, grants, and revokes against the built binary. The exempted grant is also asserted never to appear in the profile manifest.
