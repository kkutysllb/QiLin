# Agent Note: 右侧边栏作为工作台

Status: implemented

[English](2026-09-14-right-sidebar-workbench.md) | 中文

## 问题

右侧边栏已经拥有停靠套件（分栏、浮窗、两种呈现形态）、带地址认领的 tab 类型注册表、每会话一份的布局 store，以及四个随包发布的类型：`guide`、`text`、`files`、`trajectory`。除选择正文之外，每个类型与框架本身完全一样。chip 只能显示 tab 打开时捕获的标题，别的什么都显示不了。用户没有办法说「我不要这类 tab」。调用方不自己拼资源地址就打不开工作区文件，也没法把一次打开落到屏幕之外的会话。刷新之后什么都不保留：每个会话都从折叠且为空开始。一个带有实时计数——正在运行的作业、正在工作的 subagent——的页面没有地方放它。

## 决策

**类型现在自己声明身份与唯一性。** `SidebarRightTabDefinition` 新增必填的 `label: () => string`、可选的 `icon` 与可选的 `single`。`label` 无法从 `title(address)` 推导：后者命名的是打开的内容，而资源类型根本没有单一地址可命名。`single` 实现在 store 的 `openContent` 意图内部，因此「聚焦该 kind 的 tab，不限所在位置」是一条被记录的条目，并像任何其它条目一样可回放。

**chip 的状态是席位，不是字段。** 新增的键控席位 `sidebar.right.pane.tab.badge` 由拥有该 tab 的类型渲染它的徽标。徽标是实时真相，而实时真相经注册者自己的 store 或 inject compartment 抵达组件，绝不通过在别人的渲染期间读取的静态声明抵达。套件绘制徽标；它数的是什么由类型自己决定。

**套件学会了画图形；它对 `kind` 仍然一无所知。** `DockSurface` 与 `FloatLayer` 新增可选的 `renderTabIcon` / `renderTabBadge` 渲染器。chip 依次读取图形、徽标、标题，因此关闭控件的渐隐覆盖的是标题，绝不覆盖它旁边的身份标识。

**开关归注册表，持久化归插件。** 设置外壳中每个已注册类型一个开关，用它关掉一个类型。被关掉的类型失去它的引导入口——引导页是用户触达一个类型的方式，所以移除入口就是「关掉」的含义——并拒绝新的打开，而已经打开的 tab 照常渲染：不会背着用户关掉任何东西。注册表拥有被关掉的集合，因此只有一份真相；它自己过滤引导页缓存，这正是让已发布的快照保持引用稳定的原因。

**布局比页面活得久。** 停靠面 store 声明了 `persist`，因此刷新会回到用户留下的那些 tab，被清理的会话连同它的布局一起消失。记录的序列既是撤销深度也是该值的主体，因此上限设为 100 条；丢掉最旧的只会缩短回退能走多远，不影响其它任何东西。停靠面本身、它的引擎与它的席位见[停靠基础设施](2026-09-04-right-sidebar-docking-infrastructure.zh.md)。

**接口获得了调用方本来要自己拼的快捷方式。** `openFile(scope, path)` 拼出调用方本来要用 `@qilin/util-workspace-path` 组合的 `qilin-resource://file/…` 地址；两个打开选项上的 `scope` 把一次打开落到另一个会话的停靠面而不切换会话；`features` 是仓库之外的 tab 类型据以把关的能力表，因此按旧版 Sidebar 编写的类型会降级而不是崩掉。

## 考虑过的替代方案

- **`updateTab`（参考工作台的重命名/重定向调用）。** `sidebar.right.pane.tab.title` 席位已经渲染文本跟随实时状态的 chip，因此改写记录只会增加第二条改变 tab 条所显示内容的途径，而不增加任何能力。其后果记录在下方，而不是被隐藏起来。
- **引导页条目上的 `available`。** 动态谓词没有当前消费者，而引导页的条目列表为快照身份做了缓存，因此它会在两次注册表提交之间变得陈旧。
- **用 `ctx.settingsScope` 承载这些开关。** 它们是浏览器本地的视图偏好，与会话区内容宽度同属一族，而不是 Host 用户设置；localStorage 让它们按浏览器保存，无需声明任何 Host 命名空间。
- **只在提供处隐藏被关掉的类型。** 注册表同时拒绝打开，因此陈旧的调用方也无法落座用户已关掉的类型。
- **在引导页上使用 `single: true`。** 一个格最多持有一个引导页；整个停靠面的唯一性会把 tab 条的新增控件跨格拖走并破坏这条规则。席位 spec 抓到了它。

## 后果

- 设置外壳获得一个由 `ui-sidebar-right` 拥有的页面；外壳本身未被改动，该贡献通过 `slots.inject` 等待 `settings.section`。
- 开关按浏览器生效。换一个浏览器会提供所有类型。
- 单实例的*资源*类型无法重定向：`single` 聚焦已有的 tab，而没有任何东西改变它的 `contentId`。因此文件工作台每个文件开一个 tab，而不是用一个 tab 跟随所选文件——参考工作台正是靠 `updateTab` 做到后者。
- 框架之上随包发布四个页面类型：`tasks`（subagent 拓扑与后台作业，带第一个 chip 徽标）、`plans`（工作区计划文档）、`file`（CodeMirror 编辑器旁的工作区树，经新的工作区写入 RPC 保存）、`trajectory-graph`（作为节点/边图的记录表）。
- `file` 与 `text` 两个类型构成同一地址上的一对编辑/预览。编辑器工具栏经 Sidebar 控制器指名 `text` 类型打开，会话作用域取 tab 自己的——它自己的按排名打开只会落回自身——查看器的编辑控件走按排名的认领，落到编辑器；两者都复用既有对应 tab 而非重复开一个。哪些扩展名算可编辑，是 `@qilin/util-workspace-path` 里唯一的一份判定，因此一个文件要么处处可编辑，要么处处不可：编辑器的认领门槛与查看器的编辑入口读的是同一个集合。

## 验证

- `packages/client/ui-sidebar-right/tests` 覆盖注册表的开关语义、设置分区、持久化键、`single`、`openFile` 与定向打开；`packages/client/ui-dockkit/tests` 覆盖图形与徽标的渲染。
- 客户端套件跑 `pnpm run test:gui`，组装后的浏览器跑 `QILIN_SNAPSHOT=replay pnpm run test:web`。

## 延后事项

- 开关没有在浏览器场景里端到端覆盖：没有已发布的 spec 关掉一个类型并观察引导入口消失。
- 持久化只在 store 层面被断言；没有 spec 重新加载页面并观察恢复后的布局。
- 右侧边栏的格 chrome 是 76px，而会话 header 是 48px，因此该列打开时两条水平线不一致。对齐它们属于 Sidebar 自己的布局工作，不属于本次改动。
