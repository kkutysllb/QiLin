# Agent Note: 会话前入口、会话有效期与用户名

Status: implemented

[English](2026-09-16-pre-session-entry-and-usernames.md) | 中文

## Problem

未登录浏览器请求受门禁页面时会被直接送到凭据表单：部署里还没有账户时是 `/setup`，否则是 `/login?next=<路径>`。这与产品的入口流程相悖——访问者应先看到公开 landing 页，再从那里进入登录——而且退出登录也落在登录页。会话有效期是 30 天。账户只以邮箱地址为键，因此想要用名字而不是地址的部署无处记录。

## Decision

账户会话门禁把每个未登录的 index 请求重定向到公开 landing 页并带上 `?next=<请求路径>`，绝不直接送到凭据表单。landing 页读取 `GET /api/auth/status`，把它的入口按钮指向本部署能提供的文档——登录文档，或在账户文件为空时的首次运行文档——并带上经过校验的 `next` 路径，使访问者最终落到原本要去的地方。退出登录同样把浏览器导航到该 landing 页。两个会话前文档共用同一个 `?next=` 校验器（`next-destination.ts`）与同一个状态读取器（`account-status.ts`），因此开放重定向防线与事实集合各只有一个归属。

浏览器会话默认有效期为 7 天（`sessionMaxAgeDays`，绝对过期：签发时刻加配置时长，不做滑动续期），因此闲置一周的浏览器必须重新登录。

账户携带用户名与可选邮箱地址。用户名为 3–32 位字母、数字、点、下划线或短横线且以字母或数字开头，存储与查找前去除空白并转为小写，且在账户之间唯一；地址保持可选，存在时同样唯一。`setup` 与 `register` 读取 `{ username, email?, password }`；`login` 读取 `{ identifier, password }`，两种写法都接受；`change-password` 更新它给出的每个身份字段，地址为空字符串即清除。账户文件升到版本 2，并把版本 1 的记录读成"用户名即其所存地址"的账户，因此本次改动之前创建的账户仍可用地址登录。

## Alternatives considered

- 保留门禁在首次运行文档与登录文档之间的选择：被否，产品要求公开页就是入口，而一个唯一按钮会绕回门禁的 landing 页给不出入口。
- 滑动续期（每次请求重签 cookie，闲置一周才过期）：被否，它需要在 index 响应上写 `Set-Cookie` 并扩大会话面，而需求是一段固定有效期。
- 彻底去掉邮箱地址：被否，它会让已存在的账户无处安放，也放弃了运营者日后识别账户的唯一字段。
- 登录用两个字段（用户名 / 地址各一个）：被否，改为一个——查找会把两种写法归一到同一个键，第二个控件只会重复规则。
- 由服务端决定入口目标（直接重定向到 `/login` 或 `/setup`）：被否，那会让 landing 页沦为过场，而访问者看到的这一页正是本次要改变的行为。

## Consequences

landing 页与登录文档都必须保持为组合包的公开文档，因为门禁的重定向目标与入口按钮目标都必须是本服务器会应答的路径。未填地址就注册的账户永远无法用地址登录，运营者也无法用地址找回它。版本 1 的账户文件会被读成"用户名看起来像地址"的账户，因此在运营者改名之前，这些名字不满足新的用户名规则。landing 页的入口链接在一次状态读取之后被改写；状态读取失败的访问者会被送到登录页而不是首次运行页。

## Verification

`accounts-local` 规约覆盖账户文件版本 2 的结构、版本 1 的读取路径、用户名与地址的唯一性、标识符登录以及门禁到 landing 页的重定向；其夹具现在会让"某行未激活"的启动直接失败。`apps/web/tests/session-entry.spec.ts` 覆盖 `?next=` 防线（含 scheme、协议相对、反斜杠与被折叠字符的拒绝）以及 landing 页选择的三个入口目标。`ui-account` 规约覆盖未登录与已登录菜单，退出登录的导航现在断言落到 landing 页。浏览器场景 `apps/web/tests/accounts-auth.e2e.ts` 按新流程走完 landing、首次运行、登录与退出；它在当前工作树里无法执行，因为脚手架更早地失败于既存的 `ui-onboarding` 设置命名空间注册问题。
