# Agent Note: MCP 服务器由用户配置，部署不再提供推荐集合

Status: implemented

[English](2026-11-03-mcp-servers-user-configured.md) | 中文

## 问题

MCP 服务器设置页曾附带一份推荐目录——fetch、context7、sequential-thinking、playwright——可以一键添加，并用 `uvx` 与 `npx` 的逐命令可用性探测决定哪些行可以添加。这份目录是部署并不控制的第三方服务器的产品文案：启动参数会随上游包腐坏，可用性探测让设置服务依赖 subprocess 提供方，而没有这些命令的机器照样带着这份文案。清楚自己要哪个服务器的用户本来也是手写条目。

## 决策

- 部署不再提供任何 MCP 服务器定义。[`@qilin-agent/mcp-servers`](../../../../packages/mcp/mcp-servers/README.zh.md) 只对用户写入的条目提供 CRUD：`addBuiltin`、快照里的 `builtins` 字段、推荐服务器徽标与命令可用性探测全部移除，服务也不再注入 subprocess 提供方。
- 设置页保留手工编辑器——传输方式、命令、参数、工作目录、端点 URL、启动失败即失败、启停与删除。配置出来的服务器就是普通的补丁层条目，页面不对它做分类。
- 所有 MCP 服务器都来自用户配置：经[设置页](../../../../packages/client/ui-settings-mcp/README.zh.md)或 home 级 `cordis.patch.yml`。子系统参考在客户端配置旁陈述同一事实。

## 考虑过的替代方案

**保留目录但写入前要求确认。** 命令字符串与可用性探测仍会随上游包腐坏，页面仍带着部署并不支持的服务器文案。

**把目录移到 Host 作为数据。** 同样的维护负担只是下移一层，并未消失，而且除页面外没有消费方读取它。

**把目录藏在设置开关后面。** 出厂的可选项依然要持续维护，而页面的空列表才是诚实的默认状态。

## 后果

- 新机器在用户添加之前不携带任何 MCP 服务器；页面的空列表就是默认状态。
- 设置服务在挂载它的任何部署中即可激活，不再依赖 subprocess，也没有等待状态。
- 添加 context7、playwright 或任何其他服务器都变成手工条目，由用户给出 `command`、`args`、`env` 与 `cwd`。
- 页面的语言词典不再携带逐服务器描述，推荐服务器文案随中英两侧一并移除。
